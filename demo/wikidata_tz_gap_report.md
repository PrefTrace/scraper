# Отчёт: соответствие Wikidata-скрапера ТЗ

Дата проверки: 22 августа 2026 года.

## Итог

Главное изменение относительно первоначальной реализации: скрапер больше не
собирает итоговый JSON и не добавляет Wikidata-поле в `Game` из Steam API.
Теперь это отдельный асинхронный ORM-сервис. Он получает Steam AppID, находит
Q-ID через `P1733`, загружает сущности через Wikibase API и сохраняет записи в
SQLite.

Поля `languages` и `game_mechanics` в ORM-модель не входят. Факты о языке
программирования сохраняются по Wikidata property `P277`.

## Новое архитектурное поведение

ORM-модель нормализована по фактам:

- `wikidata_games` связывает Steam AppID с корневым Q-ID и хранит статус
  обновления;
- `wikidata_entities` хранит item/property, label, description, revision и
  время последней загрузки labels/full claims;
- `wikidata_facts` хранит subject, property, тип и значение утверждения;
- `wikidata_qualifiers` хранит qualifiers фактов;
- `wikidata_aliases` и `wikidata_game_links` хранят aliases и связи игры с
  подструктурами.

Для каждого объекта действуют две отметки свежести: `labels_fetched_at` и
`full_fetched_at`. Если соответствующий timestamp не старше
`SCRAPER_TTL_SECONDS`, HTTP-запрос за этим уровнем данных не делается.
При полной актуализации claims объекта заменяются одной транзакцией; JSON
снапшот в базе не хранится.

Задача запускается внутри приложения:

```python
import asyncio

task = asyncio.create_task(service.refresh_game(620))
game = await task
```

Source-сервис не создаёт task сам: это ответственность pipeline приложения.
Такой же async refresh-контракт добавлен для Steam, HLTB, Metacritic и
PCGamingWiki. Pipeline приложения создаёт `asyncio.create_task()` напрямую.

Сервис блокирует параллельные refresh одной игры, но допускает конкурентную
загрузку разных batch-ей сущностей через semaphore. Настройки берутся из env:

```text
SCRAPER_DATABASE_URL
SCRAPER_TTL_SECONDS
SCRAPER_CONCURRENCY
SCRAPER_BATCH_SIZE
SCRAPER_REQUEST_TIMEOUT_SECONDS
SCRAPER_CONNECT_TIMEOUT_SECONDS
SCRAPER_USER_AGENT
SCRAPER_PCGAMINGWIKI_MIN_INTERVAL_SECONDS
```

## Что остаётся отличием от полного ТЗ

1. Wikidata сама не гарантирует наличие всех полей для конкретной игры или
   организации. Пустое значение не всегда означает ошибку скрапера.
2. «Фактический бюджет» пока представлен через `P2130` (capital cost), так как
   в Wikidata нет единого обязательного поля actual budget.
3. Источники утверждений (`references`) не выделены отдельной ORM-таблицей;
   сохраняются сами claims, qualifiers, rank и revision.
4. События слияния/поглощения не являются полноценными event-объектами с долями,
   участниками и всеми датами.
5. Набор организационных и финансовых properties ограничен согласованным
   набором, а не всеми возможными claims Wikidata.

## Демо и замеры

`demo/benchmark_wikidata.py` теперь пишет данные в `demo/wikidata.sqlite3` и
формирует `demo/wikidata_benchmark.json` только как отчёт о времени, количестве
HTTP-запросов и числе ORM-записей. Повторный запуск на том же SQLite показывает
эффект TTL-кеша: свежие сущности не запрашиваются повторно.
